## 用户交互模式分析

### 1. 需求描述模式

**特点**: 从宏观到微观，分层递进

| 模式类型 | 示例 | 说明 |
|----------|------|------|
| 概念性描述 | "我要做的是一个Lexer生成器" | 先明确大方向 |
| 模块拆分 | "SourceLoader、ReParser、Merger..." | 架构级思考 |
| 具体指令 | "把c99.l作为一个集成测试，使用快照测试" | 精确的技术要求 |
| 问题反馈 | "刚刚内存炸了" | 直接的Bug报告 |
| 标准设定 | "不能允许20%差异。行为尽量保持完全一致" | 明确的质量标准 |

### 2. 反馈问题模式

**特点**: 快速迭代，追根溯源

1. **发现问题**: "等下 不对吧"、"刚刚内存炸了"
2. **定位问题**: "就是你运行lexer的时候内存炸了"
3. **分析原因**: "那就不该这么干 应该在第一次展开之前就做转义"
4. **明确要求**: "如果你发现了失败模式，记得先加单测再开始解决"

**反馈风格**: 直接、简洁，通常附带修复建议

### 3. 任务管理模式

**特点**: 多层级任务，子代理分工

| 层级 | 任务类型 | 示例 |
|------|----------|------|
| 顶层 | 项目目标 | "实现Lexer生成器" |
| 中层 | 阶段目标 | "完成一个可以支持其他.l测试的测试架构" |
| 底层 | 具体指令 | "推送到远程"、"生成代码覆盖率报告" |

**子代理使用**:
- 使用 `/agents` 探索能力
- 使用 `/plan` 规划任务
- 明确子代理分工：提取历史、创建测试、撰写报告

### 4. 交互频率与时机

| 阶段 | 频率 | 触发时机 |
|------|------|----------|
| 架构设计 | 高 (20条/会话) | 项目初期密集讨论 |
| 核心实现 | 中 (32条/会话) | 持续开发迭代 |
| 测试验证 | 高 (32条/会话) | 发现问题时密集反馈 |
| 项目收尾 | 中 (9条/会话) | 总结与规划未来 |

### 5. 技术风格特征

1. **测试驱动**: "在实现之前应该先给出各个模块的测试用例"
2. **严格对比**: 要求与Flex完全一致
3. **先测后修**: "如果你发现了失败模式，记得先加单测再开始解决"
4. **迭代思维**: "遵循先实现最小功能,然后迭代的原则"
5. **重视文档**: 中期报告、结项报告

用户展现出**系统化、迭代式、测试驱动**的项目管理风格。在技术上追求与行业标准工具(Flex)的一致性，在管理上采用分阶段、子代理协作的方式，在沟通上直接高效、追根溯源。整体交互模式符合典型的编译器项目开发流程：设计 -> 实现 -> 验证 -> 总结。
